## Pre-roll (not narrated)

Playwright logs in as `admin`, launches the sample, finds `v09-narrated-run`, clicks **Ship** (`/project/<id>/ship`, Package stage) and waits for the *New export* card.

## Section 1 — Cold open, Ship · Package (~00:00)

**On screen**: spotlight the stage steps, the New export card, the Options drawer.

> Now we ship. The training run produced a LoRA adapter, a small set of
> weight changes that rides on top of the base model. To deploy it, we
> merge those changes back into the base, then quantize the merged
> weights down to four bits, so the model is small and fast enough for
> modest hardware. All of this happens on Ship, in the Package stage.
> The export form is on top, and compression lives under Options.

## Section 2 — Compression setup (~00:33)

**On screen**: open **Options → Compress first**; pick the run in the *Training run* picker (fills model + adapter paths); spotlight the picker, then the section.

> Open Options, then Compress first. You pick a completed training run,
> and the model and adapter paths fill in from it. Two settings matter.
> Quantization bits: four for a tight file, eight for higher quality.
> And the output format. GGUF is the one we want, because Ollama loads
> it directly in the next video.

## Section 3 — Compress run (~00:56)

**On screen**: the spec POSTs merge-lora then quantize through the API and polls each worker task; spotlight the section.

> Now the two steps. First, merge the adapter: the trained changes fold
> into the base model and produce a full half-precision checkpoint. Then
> quantize: llama dot c-p-p converts that checkpoint to GGUF and
> crunches it down to four bits. I fire both through the API to keep the
> recording repeatable. Each step takes about four seconds on this
> hardware.

## Section 4 — Compression result (~01:22)

**On screen**: stay on the section (the panel's Result card only fills for a panel-started run); the narration carries the sizes.

> Done. The merged half-precision model was around two hundred and fifty
> megabytes. After quantization the GGUF is roughly a hundred megabytes.
> That is under half the size, small enough for a phone- class
> processor. The files sit in the project's compressed folder on disk.
> The panel's own result card only fills for a run started from the
> panel itself, so here the numbers come from the disk.

## Section 5 — Export create (~01:51)

**On screen**: pick the run and *GGUF* in the **New export** card; spotlight it.

> Back on top, the New export form. This is where we register the
> artifact against the run. Pick the experiment, then the format: GGUF.
> The quantization is four-bit, and the deployment we are aiming for is
> Ollama. That is the next video.

## Section 6 — Export run (~02:09)

**On screen**: the spec POSTs export create + run, reloads `/ship?stage=package`; spotlight **Releases** then the exports table.

> Running the export validates the file, writes a manifest with the
> model hash and a deployment plan, and registers everything against the
> run. It lands under Releases, with the exports table below: format,
> status, size, and when. This one completed. It packaged this run's
> own GGUF and nothing else: export never picks up a file that was
> compressed from another run.

## Section 7 — Wrap (~02:31)

**On screen**: hold on **Releases**.

> That is compression and export. We started with an adapter from
> training, and we end with a quantized GGUF file and a registered
> export. Publish and Deploy are the other two stages on Ship. The next
> video loads this file into Ollama and serves a real prediction.
