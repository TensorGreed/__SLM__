## Pre-roll (not narrated)

Playwright logs in as `admin`, launches the sample, stages the GGUF (`V12_GGUF_PATH`, default `data/projects/<id>/compressed/quantized_4bit.gguf`) with a one-line Modelfile and runs `ollama create slm-supportfaq`, then opens **Results → Try it**.

## Section 1 — Cold open, Results · Try it (~00:00)

**On screen**: spotlight the Try it tab, then the playground header.

> Last step. We trained, we evaluated, we compressed, and the GGUF file
> is on disk. Now we serve it. Ollama loads the model, the chat
> playground sends a prompt, and the trained model actually responds. We
> are on Results, in the Try it tab. Loop closed. Everything you have
> seen in this series comes together in one reply.

## Section 2 — Ollama register (~00:25)

**On screen**: spotlight the playground settings while the narration describes the `ollama create` step done in the pre-roll.

> First, register the file with Ollama. The recording script runs the
> ollama create command in the background. It points at the GGUF through
> a tiny Modelfile, and publishes the model under a friendly name. That
> takes a fraction of a second, because Ollama is only indexing bytes it
> already has on disk. The playground settings are here, ready for it.

## Section 3 — Playground setup (~00:51)

**On screen**: Provider → *OpenAI-Compatible / Ollama*; Model → `slm-supportfaq`; Temperature → `0` (spotlight each).

> Open the settings. The default provider is a trained run from this
> project, but to serve through Ollama we pick OpenAI-compatible, which
> covers Ollama's compatibility endpoint. The model name is the alias we
> just created. Temperature goes to zero, so the model gives its single
> most likely answer, the same one on every run. That is all the
> configuration this needs. Nothing here is specific to this one
> model. Anything Ollama can serve shows up the same way.

## Section 4 — Send prompt (~01:20)

**On screen**: type *How do I reset my password?*, click **Send**; spotlight the composer.

> Now the prompt. I will ask a question the training set covered: how to
> reset a password. The model has seen a hundred and eight customer
> support tickets, a few of them about exactly this. That is not enough
> to be excellent, but it is enough to see what it learned.

## Section 5 — Response (~01:40)

**On screen**: wait for the assistant message and the end of the reply; spotlight it.

> And there it is. Settings, then Security, then a Reset button: that
> much is exactly where the training tickets point. Then it drifts. The
> tickets say you get an emailed one-time link that expires after fifteen
> minutes. The model never mentions the email, invents a choice between
> twelve months and thirty days, and sends you to a keyring page that no
> ticket describes. Half right, confidently worded, which is what the
> evaluation's quarter F1 was telling us. And it all runs on a hundred
> megabytes of quantized weights.

The reply, at temperature 0 on the 2026-10-18 take (greedy decoding, so the
same GGUF gives it on every take): *"Open Settings → Security → Password.
Click the "Reset" button, and enter a new password for your account. You can
choose from 12 months' old or 30 days after you create it. If you're using an
external keyring, click the link in the top-right corner of Settings →
Keyring."* The spec logs it as `[v12] reply:`; if the GGUF changes, re-read
this section against the new line.

## Section 6 — Wrap (~02:02)

**On screen**: hold on the reply.

> That is the full runtime arc. We started with raw customer tickets and
> walked the workspace: Data, Train, Results, and Ship. We trained a
