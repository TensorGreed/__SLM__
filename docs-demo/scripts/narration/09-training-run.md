## Pre-roll (not narrated)

Playwright logs in as `admin`, clicks the **Demo · Support FAQ** tile, lands on the Overview, clicks **Train** in the sidebar and waits for the readiness line (`/project/<id>/train`).

## Section 1 — Cold open, the Train form (~00:00)

**On screen**: the form: base model, readiness line, Train button, then the **Runs** card title (spotlights in turn).

> Now we actually train. The first videos walked the workspace. This one
> launches a real training run on the Support FAQ sample. This is the
> Train page, and it is one form. A base model — here a hundred and
> thirty-five million parameter model, small enough to train in seconds.
> A readiness line that says whether the project can train right now. A
> Train button. And below, the Runs list, where every run and its live
> metrics stay. A real worker, a real loss curve, and a real checkpoint
> on disk at the end.

## Section 2 — Config recap, More options (~00:40)

**On screen**: open **More options**, then the **Model and hyperparameters** and **LoRA and advanced training** sections (spotlight each).

> Before we launch, a quick look behind More options. Model and
> hyperparameters holds what you would touch first: epochs, batch size,
> and learning rate. LoRA and advanced training holds the parameter-
> efficient controls — the adapter's rank, which layers it targets, the
> optimizer, and the numeric precision. The defaults are tuned for this
> hardware, and the form sizes the number of epochs to your row count by
> itself. For this recording I pin two epochs, so the run is short and
> repeatable.

## Section 3 — Kickoff (~01:15)

**On screen**: the spec POSTs the experiment create + start through the API (`page.request`, relative URLs), then reloads; the new run is the top row of **Runs**.

> Now the run. To keep the recording repeatable I create and start it
> through the API, with a fixed configuration: two epochs, batch size
> two. Pressing Train does the same thing. It asks you to confirm,
> creates the run, and hands it to the worker. Reload the page, and the
> new run sits at the top of the Runs list, queued and then running.

## Section 4 — Watching (~01:43)

**On screen**: spotlight the run row; the spec polls the status endpoint every 2 s until `completed`, then reloads so the badge flips.

> Status is running. Sixteen training steps in total. Each step is a
> forward pass, a backward pass, and an optimizer step, and the loss
> should come down across the run. On this hardware the whole thing
> finishes in about twelve seconds. Reload the list, and the badge flips
> to completed.

## Section 5 — Results, the run's dashboard (~02:04)

**On screen**: click the row's **Dashboard** button: spotlight the header, then the metrics grid (epoch, training loss, eval loss).

> Completed. Open the run's dashboard and you get the epoch counter, the
> training loss, and the evaluation loss. The final evaluation loss
> lands around five. That number is high, because the model is tiny and
> the dataset has sixteen rows, and it is a loss, not an accuracy. It
> tells us nothing yet about the answers. What matters is that the loop
> completed end to end, and there is now a checkpoint on disk, ready to
> be scored on the Results page.

## Section 6 — Wrap (~02:40)

**On screen**: **Back to Experiments**; spotlight the completed run in the list.

> That is the training loop. One form, a run in the list, a dashboard
> with the metrics. The next video scores this run against the practice
> answer key, and tells us how often the model actually got the answer
> right.

## Things to **not** say

- Don't claim the model is ready for production; final eval loss is around 5.
- Don't read env var names or REST paths aloud.
- Don't conflate a loss number with answer quality.
- The recording pins `optimizer: adamw_torch` (no bitsandbytes on this aarch64 host) and `num_epochs: 2`, which also switches the form's auto-epochs off. The run is named `v09-narrated-run`; videos 10-12 look it up by that name.
