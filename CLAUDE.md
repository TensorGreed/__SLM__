## Stack

**Backend** (`backend/`) — Python 3.12 + FastAPI + SQLAlchemy async + alembic
+ SQLite (dev) / Postgres (prod-ready). Tests use `pytest` +
`unittest.TestCase` + `fastapi.testclient.TestClient`.

**Frontend** (`frontend/`) — React 18 + TypeScript + Vite + Zustand + axios
+ react-router-dom v6. Tests use `vitest` + `@testing-library/react`.

**ML runtimes**: torch + transformers + peft (LoRA) + trl + sentence-transformers.
NVIDIA Grace Blackwell (GB10, sm_121, CUDA 13) for real training; mock /
simulate runtime for tests.

## Conventions (don't re-derive these — they're locked in)

### Phase-completion pattern
Ship phases end-to-end: backend + UI + tests + commit per phase, then
suggest the next phase. No partial phases. Roadmap statuses get updated
in the same commit. See `feedback_phase_completion_pattern` memory.

### Keep BrewSLM general-purpose
No handlers named after one domain (NER, PII, invoice). Reframe as a
task-shape + scoring_mode on a general handler. See
`feedback_keep_brewslm_general` memory.

### Update docs with code
Code changes touching CLI flags / API / glossary / workflows / demo
behavior update docs in the same commit. Stale docs > no docs in cost.

### Roadmap workflow
- `ROADMAP.md` is the active roadmap (consolidated 2026-05-28 from the
  older ROADMAP-*/SprintPlan/PLAN/CODEX_PROMPT docs, which are now
  superseded). It's **gitignored** (per project preference) — never
  commit it. Update it after shipping to keep the status accurate.
- Always end your turn with a suggested next prompt.

### Picked-data provenance
When the UI picks one entry from a list, label dataset/type/run-id so
the user can correlate. Trust payoff is large.

### Rejected rows are selectable + bulk-droppable
Batch flows with rejected rows: group by reason, let user select + bulk
drop. Never all-or-nothing.

## Database + migrations

- Dev SQLite lives at `data/slm_platform.db`. Tests use a per-PID
  scratch DB at `/tmp/brewslm-pytest-<pid>/session.db` — pinned by
  `backend/tests/conftest.py` BEFORE any test module loads.
- Engine uses `StaticPool` + a single shared connection. Cross-loop
  use breaks: don't mix `IsolatedAsyncioTestCase` with the engine —
  use `TestClient` instead (see "Testing").
- `ALLOW_SQLITE_AUTOCREATE=true` triggers `Base.metadata.create_all`
  for any new models. Existing tables are NOT migrated — you still
  need an alembic migration for column adds.
- **After committing a new migration, run `cd backend && alembic upgrade head`
  against `data/slm_platform.db` before exercising the dev server**, even
  if all tests pass. Tests run against a fresh per-PID scratch DB via
  `ALLOW_SQLITE_AUTOCREATE`, so a green test suite does not mean the
  dev DB has the new column — the dev server will 500 on
  `no such column: <table>.<column>` until the migration is applied.
  This bit on 2026-06-08 with the slice_definitions column.
- **SQLite quirk**: `ALTER TABLE ... ADD CONSTRAINT` is unsupported
  (`NotImplementedError: No support for ALTER of constraints`). For
  FKs added later, leave the constraint OUT of the migration and keep
  only the ORM-level `ForeignKey()` declaration on the column. See
  `20260526_0036_project_rag_first_columns.py` for the pattern.
- Migrations should be **idempotent** — check column/table existence
  before adding. See `20260526_0037_jobs_table.py` for the `_table_exists`
  helper pattern.

Common commands:
```bash
cd backend && alembic upgrade head           # apply pending migrations
cd backend && alembic current                # show current revision
cd backend && alembic revision -m "msg"      # scaffold a new migration
```

## Hardening / Jobs framework

Long-running ops (synth, training, RAG comparison, project cloning) run
as background `Job`s persisted to the `jobs` table. The top-bar
`NotificationBell` polls `/api/jobs/active` every 4s and surfaces
progress + outcome.

Job kinds currently:
- `synth_playbook` — `run_playbook(...)` from the synth-playbook framework
- `synth_legacy_qa` / `synth_legacy_spans` / `synth_legacy_conversations`
  — shadow jobs over the legacy `_SYNTHETIC_TASKS` registry
- `reroute_to_rag` — clone a qa-sft project into a RAG-first sibling
- `training_start` — watcher Job that mirrors Experiment progress
- `auto_rag_comparison` — UI-triggered auto-RAG comparison harness
- `post_training_lift_eval` — spawned by the `training_start` watcher when a
  real run completes (`post_training_eval_service`): base-model held-out eval
  (cached per base model until `prepared/test.jsonl` changes) + fine-tuned
  eval on the same split → paired lift. Skips simulate / baseline /
  seed-child / weightless runs; opt out via `runtime_config.auto_lift_eval=false`
  or `AUTO_LIFT_EVAL_ENABLED=false`. The shared baseline helpers
  (`find_or_create_baseline_experiment`) live here; quickstart aliases them.

Pattern to add a new kind:
1. Endpoint accepts `?async_job=true`. When true: call
   `jobs_service.start_job(db, kind, title, runner=..., project_id, params)`
   and return the serialized Job with status `202`.
2. Runner is `async def _runner(handle: JobProgressHandle) -> dict`.
   Use `handle.set_progress(fraction, message)` to publish updates.
3. **0-rows or no-op success should raise** — silent "Done" with empty
   results misleads the user. See `synthetic.py` + `synth_legacy` bridge
   for the pattern + the diagnostic-error format.
4. Frontend: deep-link in `NotificationBell.jobDeepLink()`. Per-kind
   outcome summary in `NotificationBell.jobOutcomeSummary()`.

Runner caveats:
- Hold strong refs (jobs_service does this via `_RUNNING_TASKS`) — the
  GC will silently kill a task whose only ref was a local var.
- Atomic transitions: `UPDATE WHERE status=QUEUED` for QUEUED→RUNNING
  so a cancel landing mid-transition isn't clobbered.
  That UPDATE can still be lost on the shared single-connection engine
  (another session's ROLLBACK between the UPDATE and its COMMIT — the
  lift-check Job sat in QUEUED, `started_at` NULL, for its whole run). The
  wrapper re-checks after committing and re-applies once, and
  `JobProgressHandle.set_progress` promotes a still-QUEUED Job to RUNNING
  (a runner reporting progress is running). Terminal statuses are never
  touched by either.
- For sync/GPU-bound work: `asyncio.to_thread(...)` + a separate
  drainer task polling shared state. See
  `api/auto_rag.py:run_auto_rag_comparison` for the pattern.

## Testing

### Backend
```bash
cd backend && python -m pytest tests/test_X.py          # one file
cd backend && python -m pytest tests/                   # all
cd backend && python -m pytest -k "name_pattern"        # by name
```

- `tests/conftest.py` pins `DATABASE_URL` + `DATA_DIR` to `/tmp` BEFORE
  any module loads. Don't override these in test files — the conftest
  wins.
- For module-level test classes that need the FastAPI lifespan
  (init_db, etc.), open a `TestClient` at module level via
  `setUpModule` / `tearDownModule`. See
  `tests/test_jobs_service.py` for the pattern.
- **Avoid `IsolatedAsyncioTestCase`** for code that touches the
  SQLAlchemy engine — each test method spawns its own event loop and
  the StaticPool-pinned aiosqlite engine doesn't survive loop swaps.
  Drive via `TestClient` (which runs the app in its own thread) or
  via raw `asyncio.run` from a sync `unittest.TestCase`.
- For tests that need to seed Jobs / Experiments / etc. without going
  through endpoints, use `app.database.async_session_factory()` +
  `asyncio.run(...)`.
- **CI test scope.** `ci.yml`'s `backend-tests` job runs the `test_phase*`
  modules under `python -m unittest` (one shared process) **plus** a second
  step that runs every **non-`test_phase`** file in **its own `pytest`
  process** (`pip install pytest` then a per-file loop). Per-file isolation is
  mandatory: several non-phase files (`test_jobs_service`, `test_demo_project_reset`,
  `test_classification_training_launch`, the `test_probe_*` files) override
  `DATABASE_URL` at import, so two in one pytest process collide on the single
  StaticPool engine. The non-phase files are pytest-developed (they rely on
  `conftest.py`'s per-PID `/tmp` DB pin) and several **fail under bare
  `unittest`** (no conftest) — keep them on the pytest loop, don't fold them
  into the unittest job. The loop retries each file up to 3×. The original reason —
  async-job tests (`test_jobs_service`'s heldout / quickstart / llm-judge
  endpoints, `test_distillation_teacher_capture::test_run_event_emitted`)
  failing ~1-in-8 with "Project N not found" / a missing RunEvent — is fixed
  at the root: on the shared StaticPool connection a read-only session's
  ROLLBACK (`Session.close()` / pool reset-on-checkin) discarded another
  session's flushed-but-uncommitted writes; `app/database.py`'s rollback
  guard skips the DBAPI rollback for checkouts that executed no DML (only on
  the SQLite StaticPool engine; regression test
  `tests/test_shared_connection_rollback_guard.py`). The retry stays as a
  safety net for load-dependent timeouts (e.g. the 1.2 s base-model
  introspection in `training_preflight_service._infer_model_capability`); a
  genuinely broken file still fails all 3 attempts. Tests that start Jobs
  must still wait for them in tearDown — `from _job_wait import
  wait_for_jobs_idle` (raises naming the in-flight Jobs) — because a Job
  alive at TestClient shutdown hangs the process.

- **Real-runtime gate** (`tests/test_real_training_path.py`, CI job
  `real-training`): drives a LIVE stack over HTTP (backend on
  `TRAINING_BACKEND=external` + Redis + a Celery worker) — project → support-faq
  sample → experiment → start → Celery → `python scripts/train.py` → COMPLETED →
  watcher Job → automatic lift check → `/evaluation/summary` with row evidence.
  Skips unless `BREWSLM_REAL_TRAINING_BASE_URL` is set, so the per-file loop
  ignores it. CPU-only on CI (SmolLM2-135M, `num_epochs=1`,
  `AUTO_LIFT_EVAL_MAX_SAMPLES=8`, `AUTO_LIFT_EVAL_MAX_NEW_TOKENS=48`); the HF
  model is cached by `actions/cache`. Path-integrity, not quality: the lift may
  read "within noise". **Documents-project gate** (same file,
  `DocumentsProjectGateTests`): synthetic statute → upload → clean → the
  documents → Q&A flow with `backend="template"` → the pre-training passages
  gate (real base-model inference on CPU, judged by the template judge) →
  stop + Coach/summary assertions, "train anyway" → COMPLETED → judged lift
  → `passages_vs_finetune` readable. The job env sets
  `BREWSLM_TEMPLATE_SYNTH=1 EVAL_JUDGE_BACKEND=template`, so the support-faq
  test's headline is `judge_correct` there (it accepts f1 or judge_correct).
  **Template backend** (`synth_backends/template.py`): deterministic stand-in
  for a generation / judge model — pairs lifted from passage sentences,
  verdicts by token overlap; registered LAST and available only with
  `BREWSLM_TEMPLATE_SYNTH=1` (never auto-picked on a dev box); refuses any
  other prompt. The synthetic statute lives in both the pytest file and
  `tests/golden-path/golden-path-documents.spec.ts` — keep them in sync. Locally: boot a scratch backend + worker with the same
  env and run the file with the URL set — the dev worker must NOT be running
  on the same broker DB, or it consumes the task with the wrong DATA_DIR.
  **CPU dtype**: transformers ≥ 5 loads a checkpoint in its *saved* dtype
  (bf16 for most small instruct models). On a CPU without native bf16 (AVX2
  x86 — half of GitHub's runners) bf16 is emulated: a training step took
  ~230 s instead of ~5 s. `train.py`, the eval loaders
  (`evaluation_service._inference_dtype`) and `local_chat_service` load
  **fp32 on CPU**, bf16/fp16 on CUDA. Any new `from_pretrained` must pass a
  dtype — never rely on the default.
- **Real-training tests** (`test_training_correctness`, `test_continued_pretraining`,
  `test_export_scoping_and_merge`, `test_playground_trained_run`) fine-tune /
  load SmolLM2-135M. They run only with a GPU or `BREWSLM_REAL_TRAINING=1`
  (and a cached model); `BREWSLM_SKIP_REAL_TRAINING=1` forces a skip. CI has
  neither, so they skip there.
- **Never open a `TestClient(app)` outside pytest** (an ad-hoc `python -`
  probe, a script). Without `conftest.py`'s DB pin it boots the app against
  the DEV `data/slm_platform.db`, and the lifespan's startup sweep marks every
  QUEUED/RUNNING job there FAILED (`lost_during_restart`) — on 2026-10-13 it
  swept a documents→Q&A flow that was still running in the real backend
  (the runner's own `_finish_job` later overwrote FAILED with SUCCEEDED, so
  the result survived, but any waiter keyed on the status moved on early).
  Probe the running backend over HTTP instead.
- **Tests that spawn background Jobs must let them finish** (cancel runs they
  start, wait on `/api/jobs/active?include_recently_completed=false` in
  `tearDown`) and must never poll the engine via `asyncio.run` from the test
  thread — on the shared StaticPool connection both wipe the next test's
  writes ("Project N not found", "Could not refresh instance", "Lock … bound
  to a different event loop"). And never let a Job run a real model eval
  (patch `run_heldout_evaluation`): on CI it downloads + runs on CPU and the
  process hangs at exit. Also stub synth backends (patch **both**
  `synth_backends.BACKEND_REGISTRY` and `synth_playbook_service.BACKEND_REGISTRY`
  — the service binds its own copy) or the runner probes/uses a real Ollama and
  outlives the test; and make fake runners hold ~0.5s before failing so a
  follow-up request doesn't race the FAILED write (see `test_jobs_service`).
  CI caps each non-phase file at 600s
  (`::error::<file> timed out`) and the job at 90 min.

## CSS / ARIA lint quirks (strict mode)

- **Inline styles** flagged as warnings by the linter. Use bucketed CSS
  classes for dynamic widths (e.g.
  `.notif-bell__progress-fill--w-50 { width: 50%; }`). Snap dynamic
  values to nearest 10% in the JSX.
- **ARIA dynamic attributes** flagged as errors (`aria-expanded={bool}`,
  `aria-valuenow={int}`). Strict validator wants literal strings;
  can't see through JSX expressions. Drop the dynamic ARIA and use
  `aria-label="N% complete"` for screen-reader content.
- Pre-existing inline-style warnings throughout legacy files
  (TrainingPanel.tsx, CoachSuggestion.tsx, EvalPanel.tsx) — don't
  treat them as regressions when your edit triggers a hook diagnostic.
